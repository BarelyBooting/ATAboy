# ATAboy (BarelyBooting fork)

This is a fork of [ATAboy](https://github.com/redruM0381/ATAboy), the open-source IDE-to-USB bridge by redruM0381. The hardware, the firmware and the whole idea are theirs. For what ATAboy is and how to use it, start with the upstream [README](README.md) and repository.

I use ATAboy to image some old drives that can't be replaced, so I've been fixing a few things I ran into. The author mentioned on [issue #13](https://github.com/redruM0381/ATAboy/issues/13) (Aug 2026) that a fix there "may be as late as spring 2027", so this fork keeps the firmware building and carries a handful of small, tested fixes in the meantime. Each one is also sent upstream as its own pull request. It isn't meant to replace the original project.

## What's different

The fork's firmware lives in [`FW source/v.6f3p1/`](FW%20source/v.6f3p1/) on the `palimpsest/dev` branch. It's upstream v.6f3 with these changes:

1. **Reads past the end of the drive no longer come back as zeros with a success status.** Upstream zero-fills any part of a READ(10) at or beyond the configured sector count and reports success, which looks exactly like real data. Now it returns only the sectors it actually read and fails the rest. The firmware sets sense 5/21 (LBA out of range), though the host currently sees 2/3A instead because TinyUSB rewrites the sense on failed reads. That's a separate TinyUSB issue. You can get the old behaviour back with `-DATABOY_STRICT_MEDIA_BOUNDS=0`. I tested this one on hardware (40 GB Maxtor, LBA mode): reads past the end now fail with nothing written to the host buffer, and real sectors read back byte-identical to the stock firmware.

2. **MODE SENSE(10) can't overrun its buffer any more.** The TinyUSB in pico-sdk 2.2.0 passes the host's requested length through as the buffer size, and the MODE SENSE handler memsets that many bytes into a 4 KB buffer. It's now clamped. Built and checked in the disassembly, but deliberately not triggered on hardware.

3. **Esc actually cancels manual CHS entry.** It used to fall through and apply whatever geometry was in the input fields. Built and flashed, not yet exercised on hardware.

4. **Dismissing the detect error box flags a media change**, like every other unmount path already does. Built and flashed, not yet exercised on hardware.

5. **`pico_sdk_import.cmake` is included**, so the source builds as-is. Upstream v.6f3 references it but doesn't ship it.

Added in 0.6f3p4 (built and host-tested, not yet run on hardware):

6. **ATA PASS-THROUGH, read-only.** The bridge now answers ATA PASS-THROUGH(12) and (16) for IDENTIFY DEVICE and READ SECTORS / READ SECTORS EXT (PIO, 1 to 8 sectors per command, LBA mode), so tools can read the drive's own identity and read sectors with the ATA command they chose. Everything else is refused with ILLEGAL REQUEST before anything is sent to the drive: writes, DMA, SMART, other protocols. (Data-out direction can't be fully checked from inside the callback, but only the read-only commands above can ever run.) The allowlist is one small pure file, `sat_policy.c`, with an exhaustive host test and mutation tests in `test/`. Build with `-DATABOY_SAT=0` to leave it out. Built and host-tested, not yet tried on hardware.

7. **[Issue #13](https://github.com/redruM0381/ATAboy/issues/13): one bad sector no longer fails a whole multi-sector read.** The host gets every good sector before the bad one, then an error, and can read the rest one at a time. A failed sector is never filled in, and any flawed data the drive offers with the error is thrown away. The firmware no longer soft-resets the drive after an ordinary read error; it still resets on a timeout. The drive's error registers are saved before any reset, and Debug Mode's "E" shows them.

8. **Status polls wait for BSY to clear before looking at ERR or DRQ**, and wait 400 ns after each command before the first status read, as ATA requires. Before, an ERR bit seen while the drive was still busy could end a command early.

9. **[Issue #9](https://github.com/redruM0381/ATAboy/issues/9): the whole 80x24 screen is painted blue**, instead of relying on the terminal to erase in the current colour (GNU screen doesn't, by default). **Ctrl+L redraws the screen.**

10. **A soft reset now waits for the drive and checks the CHS geometry came back.** Before, the firmware waited 2 s after a soft reset and then sent INITIALIZE DEVICE PARAMETERS whether the drive was ready or not. ATA gives a drive up to 31 s. A slow drive ignored the command, fell back to its own default translation, and every later CHS read went to a different sector than the one asked for, with good status. Now the reset waits up to 31 s, selects the drive again (a reset always selects the master, which broke slave drives), and in CHS mode refuses reads and writes until the drive has accepted the geometry. Debug E shows "no geometry" or "reset FAILED" when that happens. The drive is also no longer handed a new command while it is still offering data from an earlier one; that check used to be part of item 6 only.

11. **READ(10) and WRITE(10) refuse a malformed request.** TinyUSB works the block size out from the host's transfer length and never checks it is 512, so a length that didn't match the block count could make the partial-sector code copy past a 512-byte buffer. A request that isn't whole 512-byte sectors is now refused before anything is read or written. Normal operating systems never send one.

12. **A slave drive on its own survives a soft reset.** Found on real hardware in 0.6f3p4 (a Seagate with no jumpers, which makes it a slave, alone on the cable): after a soft reset the firmware waited for a master that wasn't there. An empty master position reads 0xFF on this bus, which looks busy, so it waited the full 31 s and then gave up with the empty position still selected. Every command after that failed until the next detect. Now a slave stops waiting as soon as the empty position reads 0xFF, and is selected again. If there is a master on the cable (a saved setup can mount a slave without probing), the slave waits for the master to finish its reset first, since selecting it earlier can be lost. A master that times out is left alone.

13. **Host tests** in `tests/host/`: the real `ide.c` and `usb.c` run against a simulated drive (`run.sh`, `mutate.py`), and `tui_compare.py` checks the screen output against an older build.

Added in 0.6f3p6 (built and host-tested, not yet run on hardware):

14. **ATA PASS-THROUGH can ask the drive about itself.** Item 6's list now also has SMART READ THRESHOLDS and READ LOG (PIO data-in, as before), and two non-data commands: READ VERIFY SECTORS, and READ NATIVE MAX ADDRESS in its 28-bit and 48-bit forms. READ NATIVE MAX shows whether a drive has a Host Protected Area, which matters when imaging, since such a drive reports fewer sectors than it has. SET MAX ADDRESS, which would change that, stays refused, as do DCO, the security commands and every write. SMART READ DATA and SMART RETURN STATUS are left out of the normal build on purpose: ATA-3 says a drive saves its attribute values to non-volatile memory before answering either one, so on a drive from the mid 1990s they write to the drive. Building with `-DATABOY_SAT_SMART_SAVES=1` puts them back, for drives where that doesn't matter. With CK_COND set, or when the drive reports an error, the host gets the drive's registers back as an ATA Status Return descriptor in descriptor-format sense, so it can read the answer, or the LBA where a read or verify failed. That sense is 22 bytes; a host that asks for less gets it cut short. SMART and READ NATIVE MAX also work in CHS mode, since they don't name a sector. Reads and verify are still LBA mode only. SMART, READ NATIVE MAX and READ SECTORS EXT only go to a drive whose own IDENTIFY data, read by the firmware when it detected the drive, says it supports them (words 82 to 84, which drives older than ATA-4 don't fill in). With no such IDENTIFY, for instance after forcing a manual geometry, they're refused. Before sending one of them, the firmware also asks the drive for IDENTIFY again and checks the serial, model and those words still match, so a drive swapped on the cable after detection isn't judged by the one that was there before. Some old drives write to themselves on a SMART read (a Conner CFS1275A saves its attribute values on every READ DATA), so the bridge doesn't guess. A pass-through command also isn't taken as finished until the drive has visibly started it (BSY seen, or INTRQ). Before that the status still shows the previous command, and reading the registers then would hand back what the host wrote as if it were the drive's answer. A command that never starts is aborted with a soft reset and reported as failed. A device fault (DF) is reported as a hardware error on every pass-through path. Built and host-tested, not yet tried on hardware.

15. **Firmware updates without the BOOTSEL button.** On the main menu, with no drive mounted, press **Ctrl+F** and answer **Y** to "Enter firmware update mode (Y/N)?". The ATAboy reboots into the RP2350's own bootloader, the same mode holding BOOTSEL gives, so a new UF2 can be copied over or loaded with picotool. The button still works as before and is the way back if a build won't start. Ctrl+F does nothing while a drive is mounted. If a USB transfer that started before the unmount is still running, Y waits for it (up to a minute) and won't reboot under it. The key was B at first, but a Down arrow whose escape sequence arrives split can reach the menu as a bare B; no escape sequence can produce Ctrl+F.

Added in 0.6f3p7 (built and host-tested, not yet run on hardware):

16. **Sector reads and writes wait by the clock, and for as long as the host will.** Found on real hardware in 0.6f3p6: a Seagate alone on the cable as a slave took longer than usual to finish one single-sector write, and the firmware reset it in the middle of it. The wait after a write counted polls, about a second's worth, instead of time. The sector had been written; the drive just hadn't said so yet. After that reset the drive stayed busy and then stopped answering altogether until the next detect. Every wait on a read, a write or IDENTIFY is now against the clock. A read or write gets up to 15 seconds from the command to the end, the whole command and not each sector, and IDENTIFY gets 10. Item 20 says why 15.

17. **A drive that doesn't come back from a soft reset gets one hardware reset.** The firmware now pulses the IDE reset line, the same one Auto Detect uses, then selects the drive again, waits up to the 31 seconds ATA allows, sends RECALIBRATE, waits for it to finish, and puts the CHS geometry back. It only tries once per failure, however many USB commands the wait takes (item 20). The reset line resets both drives on the cable. Debug E shows "HW reset" when this was needed, or "HW reset FAILED" when even that didn't bring the drive back.

18. **SMART pass-through also needs SMART to be switched on.** A drive can support SMART and have it disabled, and then it refuses every SMART command (the same Seagate: supported, not enabled). SMART commands now only go to a drive whose IDENTIFY word 85 says SMART is enabled, and only when word 87 marks word 85 as valid, the same check Linux makes. Which pass-through commands need the IDENTIFY re-check from item 14 now comes from the allowlist itself, so the two can't drift apart. IDENTIFY itself also no longer takes an error left over from the previous command as its own answer.

19. **Auto Detect and Debug Mode wait for a USB command that's still running.** After an unmount, a slow command that started before it can still be using the drive. Detect and the debug keys now wait for it instead of using the IDE bus at the same time. The wait can't be cancelled and shows nothing while it lasts, because the console goes through the same USB side that is busy; it ends when the command does, 20 seconds at most (item 20). Then the key does nothing and says a USB command was running, so you can look at what happened and press it again. A build with `-DATABOY_SAT_SMART_SAVES=1` now calls itself `0.6f3p7-palimpsest-smartsaves` and shows `(fork+smartsaves)` in the setup screen, so it can't be mistaken for the normal build.

20. **Each USB command gets 20 seconds, everything included.** A host gives up on a command after a while and then resets the whole USB device: Linux after 30 seconds, the palimpsest tools after 30, Windows after 10 unless the registry says otherwise. The first 0.6f3p7 build gave each ATA command 30 seconds, the retry at a bad sector from item 7 another 30, and each reset its own 31, so one stuck read could keep the firmware busy for one or two minutes, long after the host had reset the device underneath it and thrown away the good sectors item 7 is there to return. Now everything the firmware does for one USB command (the reads, that retry, any reset) fits in 20 seconds. The drive gets up to 15 of them for the work itself, so there is time left to reset it if it hangs. If a reset hasn't brought the drive back when the 20 seconds are up, the host gets its error then, and the next command carries on waiting for the drive before it sends it anything. The hardware reset from item 17 still happens at most once per failure, and a write is never sent to the drive a second time by the firmware. Debug E says "Reset still running" meanwhile, and pass-through commands that had to be aborted now show up in Debug E too. IORDY is ignored after a hardware reset until the drive is back, since a drive that never comes back holds it low and would hang the firmware. On Windows, set `HKLM\SYSTEM\CurrentControlSet\Services\Disk\TimeOutValue` to 30 or more, or Windows will cut off a command when a drive spends more than 10 seconds retrying a sector.

21. **A read or write only goes to the drive with time to finish it.** Item 20's 20 seconds cover a whole USB command, but a long READ(10) or WRITE(10) reaches the firmware in 4 KB pieces of 8 sectors, and a later piece could be sent to the drive with only a few milliseconds of them left. A healthy drive can't finish in that, so the firmware gave up on it and reset it: a 128-sector read from a drive taking 120 ms a sector was reset on every try, where 0.6f3p6 read it without one. Now a read or write of n sectors is only sent with at least 1.1 seconds times (n + 1) of the 15 still ahead of it, which is about what 0.6f3p6 allowed it (its polls came to a little over a second per sector). Otherwise nothing is sent, the USB command fails, and Debug E says "no time". So a reset only follows a command that had as long as 0.6f3p6 would have given it. The retry at a bad sector from item 7 is only sent with as long again as the sector took the first time; without that, the host gets the good sectors and an error. The price: a 128-sector read only completes if its first 120 sectors take about 5 seconds or less (about 42 ms a sector), and a sector that takes more than about 5 seconds to read makes the rest of that read fail. Nothing is lost and nothing is reset; read in pieces of 8 sectors (4 KB) or fewer, which always get the whole 15 seconds. Pass-through commands likewise only go out with their whole 10 seconds. After a reset in CHS mode the geometry is only sent with its whole second, or at the start of the next USB command, and Debug E no longer calls the reset failed when there just wasn't time. Switching IORDY on in Features while a drive is still coming back from a hardware reset no longer undoes item 20's hold; the setting takes effect once the drive is back, and while a drive is mounted, at the next USB command.

Added in 0.6f3p8 (built and host-tested, not yet run on hardware):

22. **Manual CHS without IDENTIFY.** Some old drives shouldn't be asked who they are before they're given a geometry. The one that started this is a 1990 Conner CP3044, whose manual never calls it ATA and has no IDENTIFY in it. Both existing ways to type in a geometry come after Auto Detect, and Auto Detect always sends IDENTIFY first, even when it's going to fail. On the main menu, with nothing mounted, **Ctrl+G** now opens a "Manual CHS (no IDENTIFY)" box with fields for cylinders, heads and sectors per track. Nothing goes to the drive while you type, and Esc leaves everything as it was. Values the drive can't be given are refused on the spot with the reason (cylinders 1 to 65535, heads 1 to 16, sectors 1 to 255); before, they wrapped around or lost their top bits without a word. Once the numbers are in range it asks once more, and only Y sends anything: a reset on the IDE reset line (both drives on the cable see it), a wait of up to 45 seconds for the drive to stop being busy, RECALIBRATE, and INITIALIZE DEVICE PARAMETERS with your heads and sectors. That's what a PC/AT BIOS sends a drive whose type was typed in, and nothing else goes out, no IDENTIFY and no SET FEATURES. The geometry only counts if the drive accepts it. If it refuses, or doesn't answer, the screen says so, the geometry reads 0 so there's nothing to mount, and Debug E shows the registers. Ctrl+G doesn't save anything to EEPROM, and it won't run while a reset from an earlier USB command is still pending; Debug R ends that. Every reset now counts as losing the geometry: Debug R, Auto Detect's, the one Auto Mount does at power-up, and those after a failed read. The next CHS read or write sends the geometry again before it touches a sector, and refuses if the drive won't take it. Before, Ctrl+G followed by Debug R read the wrong sectors with no error, and stock v0.6f3 does the same after Debug R with any CHS geometry. Auto Detect now starts by clearing the geometry, so leaving its picker (or F: Force) with Esc leaves nothing to mount rather than the old numbers against a drive that was just reset, maybe a different one. While the geometry in use came from Ctrl+G, ATA pass-through refuses every command, IDENTIFY included, so smartctl, smartd or CrystalDiskInfo can't ask the drive what Ctrl+G avoided asking; an Auto Detect that the drive answers lifts it (up to 0.6f3p9 a Debug I did too; since 0.6f3p10 Debug I isn't sent after a Ctrl+G, item 27). F10 won't save a Ctrl+G geometry while Auto Mount is on, because Auto Mount resets the drive and sends IDENTIFY at every power-up; with Auto Mount off it saves as usual. One gap is left: the saved setup doesn't record where a geometry came from, so after a power cycle nothing stops you turning Auto Mount on and saving again. Keep Auto Mount off for a drive like this. Auto Detect's F: Force route is otherwise unchanged.

Added in 0.6f3p9 (built and host-tested, not yet run on hardware):

23. **Each ATAboy reports its own USB serial number.** Upstream gives every unit the serial number 654321, so a PC with two of them attached can't tell them apart. The serial is now the RP2350's unique board id, 16 hex digits, the same on every power-up and different on every unit. Windows and Linux key a device on its serial number, so after updating, the ATAboy shows up as a new device once: expect a different COM port number (and a new `/dev/disk/by-id` name on Linux). Scripts that name the port need changing.

24. **A warning when IORDY is on and the drive doesn't say it supports it.** With IORDY enabled in Features, and the drive's IDENTIFY word 49 without bit 11 (IORDY supported), a yellow line saying "IORDY on; drive does not declare IORDY" appears on the geometry picker after Auto Detect (not the F: Force one, which has no IDENTIFY), and on the main and Features screens. It only says so. The setting isn't changed and nothing is sent to the drive for it. Drives older than ATA-2 leave word 49 at 0000h, which is why it says "does not declare" and not "unsupported". The word comes from Auto Detect's or Auto Mount's IDENTIFY; after Ctrl+G, which sends none, the line never shows.

25. **The data a drive offers with a failed sector is kept, and only READ BUFFER hands it out.** Item 7 reads and throws away the flawed data some older drives offer along with an error. Now those 512 bytes are kept instead, with the drive's status, error and command, the sector number and the time. It's the same reads as before and nothing extra goes to the drive. The READ(10) fails exactly as it did: same error, same good sectors before it, and none of these bytes, which never go anywhere a normal read, pass-through read or image can see. The only way to get them is SCSI READ BUFFER(10) exactly as: opcode 3Ch, mode 02h (bits 4 to 0 of byte 1), buffer ID 5Ah, buffer offset 0, allocation length in bytes 6 to 8. Anything else is refused with ILLEGAL REQUEST, 24h/00h (invalid field in CDB), and no data. The answer is 544 bytes, cut to the allocation length: bytes 0 to 7 `ATBSALV1`; 8 is 1 when there is a capture and 0 when there isn't (then everything after it is 0); 9 the ATA status (ERR and DRQ set); 10 the ATA error register; 11 the ATA command (20h, or 24h on a 48-bit mount); 12 to 15 the sector the host asked for, little-endian, numbered as the host numbers sectors whether the drive is mounted in LBA or CHS; 16 to 19 a sequence number, 1 for the first capture since power-up and one more for each after, so a host can tell a new capture from one it has seen; 20 to 23 milliseconds since power-up at the capture; 24 to 31 zero; 32 to 543 the 512 bytes as the drive offered them. There's one capture, replaced by the next, and only power-up clears it; READ BUFFER works with or without a drive mounted and doesn't touch the drive. When a multi-sector read fails, TinyUSB asks again at the failing sector (item 7), so one bad sector can make two captures and move the sequence on by two. For example, on Linux: `sg_raw -r 544 /dev/sdX 3c 02 5a 00 00 00 00 02 20 00`. Debug E shows the latest capture on a line of its own ("Salvaged #n: LBA ..."); there's no room for it beside "drained" on the register line. What these bytes are is up to the drive: the Conner CFS1275A manual says its flawed data still reaches the buffer on an uncorrectable error, most manuals say nothing. They're evidence, not good data.

26. **READ LONG, through SCSI READ LONG(10).** READ LONG gives a sector's data as the drive has it on the platter plus 4 vendor specific (ECC) bytes stored with it, without the drive checking or correcting them, so a sector that fails an ordinary read with an ECC error normally comes back with good status. A host sends SCSI READ LONG(10) (opcode 3Eh, LBA in bytes 2 to 5, byte transfer length in bytes 7 and 8), and the firmware sends the drive READ LONG WITHOUT RETRIES (23h) for that one sector, addressed exactly as a READ(10) of it would be (LBA28, or CHS through the mounted geometry, sent again first if a reset dropped it). The answer is 516 bytes: the 512 data bytes and then the 4 vendor specific bytes. Why 4: ATA-3 (X3T13/2008D rev 7b) says in 2.1.7 that the default number of vendor specific bytes on READ LONG is four, and in 7.7.12 and 7.16 that a drive only sends 512 plus its IDENTIFY word 22 after a SET FEATURES that switches it to that length. This firmware never sends SET FEATURES, so word 22 doesn't set the length (a Maxtor 2F040L0 says 57 there; by the standard it still sends 4); Debug I shows it. 7.16 also says each of those bytes comes in bits 7 to 0 of one 16-bit transfer, which is how they're read, with DRQ checked before each one, and that READ LONG needs PIO mode 0, the only timing this bus uses (400 ns DIOR-, 700 ns cycle). Nothing new goes to the drive unless a host asks for READ LONG. It's refused, before anything reaches the drive, when: nothing is mounted (NOT READY, 04h/00h); CORRCT or PBLOCK is set (ILLEGAL REQUEST, 24h/00h: only uncorrected data is ever asked for); the geometry came from Ctrl+G (24h/00h); the drive didn't answer the firmware's own IDENTIFY at detection, or it's mounted 48-bit, where there is no READ LONG (ILLEGAL REQUEST, 20h/00h, command not supported); the command doesn't come with a data-in CBW (24h/00h), since the data could never reach the host; the byte transfer length isn't 516 (ILLEGAL REQUEST, 24h/00h with ILI set and the INFORMATION field holding the requested length minus 516, as SBC has it, so a tool can learn the right length from one try); the host's transfer length is shorter than 516 (24h/00h); the sector is past the end of the mount (21h/00h, as READ(10)). A byte transfer length of 0 is not an error in SBC and gets GOOD with no data and nothing sent. Then, from the drive: the data (GOOD); ABRT and no other error bit, which ATA-3 7.16 says means the drive doesn't support READ LONG (ILLEGAL REQUEST, 20h/00h); any other error from the drive (MEDIUM ERROR, 11h/00h, as READ(10)); nothing sent because a reset is still pending, there wasn't time or the drive wasn't ready (NOT READY, 04h/00h); or no data in time, or the drive offering more or fewer than 4 vendor specific bytes (ABORTED COMMAND, 00h/00h). DRQ gets up to a millisecond to drop after the last byte before the drive is taken to have more. Errors are recorded for Debug E as a read error, a timeout or a bad end, with a soft reset whenever the drive was left still offering data. It keeps to the same time budget and checks as a READ(10) of one sector (items 16 to 21). It hasn't been tried on a drive yet. READ LONG is optional in ATA-3 and marked for removal, so plenty of drives won't have it. The text of the standard quoted here is in palimpsest's `docs/research/ATA3-READ-LONG-2026-09-24.md`.

Added in 0.6f3p10 (built and host-tested, not yet run on hardware):

27. **Ctrl+G can leave out INITIALIZE DEVICE PARAMETERS altogether, if you ask it to.** Item 22 always sends 91h. The drive it was written for, the 1990 Conner CP3044, powers up in its native 522/4/40 according to its manual, and the manual of its 1989 sibling, the CP3024, says the values in a 91h aren't checked and that 91h only switches that drive to translation when the sectors per track are 17. So the Ctrl+G box now has a second mode. It's opt-in: every Ctrl+G opens the box exactly as before, byte for byte, and Y there sends what item 22 sends. Pressing Ctrl+G again while typing a field switches the box to "Manual CHS (no IDENTIFY) - power-up default, no 91h", with a yellow line saying it's only for a geometry that IS the drive's power-up default (Ctrl+G again switches back). The question then reads "Y: reset Master, keep C/H/S, no 91h   N: edit", and Y sends the reset on the IDE reset line, waits up to 45 seconds for the drive, sends RECALIBRATE, and nothing else. The drive must then show ready (DRDY) within a second with no error left by RECALIBRATE. If it doesn't, the screen says "Manual CHS: drive not ready, no 91h", nothing is set, and Debug E shows "not ready after 10h (no 91h)". A drive that only sets DRDY after a 91h can't be used this way; its reads would fail anyway. Once accepted, Current HDD reads "Manual CHS (no IDENTIFY) no 91h", and 91h is never sent to the drive: not after Debug R, not after a soft or hardware reset during a read, and not when a reset carries over into the next USB command. A reset puts the drive back in its power-up default, which is the geometry in use, so there's nothing to put back. That lasts while the geometry, the device and CHS mode are the ones it was set with. It ends at a power cycle of the ATAboy, at a later Ctrl+G once that one sends anything (Esc, N or a refusal before Y leaves it as it was), and at unmount. (Until item 28, Auto Detect ended it too; after a Ctrl+G, Auto Detect is now refused.) Unmount also clears the geometry, so Mount has nothing to mount until a new Ctrl+G: with nothing mounted the drive can be powered off or swapped, and nothing would notice. A USB read that started before the unmount can still be running, even in the middle of a reset, so the unmount waits for it (up to 25 seconds, with the screen still) before it ends the mode; if the read is still going after that, the mode is left as it is and only Mount is refused. Either way, a drive mounted in this mode gets no 91h at all until the next Ctrl+G that sends anything, even after the mode has ended, and no 91h ever goes out for 0 heads or 0 sectors. Current HDD keeps saying it was a Ctrl+G drive until the ATAboy is power-cycled, so the host tools still see what the drive was. After the unmount it still reads "Manual CHS (no IDENTIFY) no 91h", with the geometry at 0/0/0. Mount then says "Manual CHS: geometry cleared, Ctrl+G again", and once that box is dismissed Current HDD reads "Manual CHS (no IDENTIFY) cleared". Dismissing the error box of a failed Ctrl+G, in either mode, also leaves "Manual CHS (no IDENTIFY) cleared"; before, Current HDD went back to "IDENT not run yet". Everything else is as in item 22: no ATA pass-through, no READ LONG, reads only within cylinders x heads x sectors, and the 45 second wait. Write protect is forced on for a Ctrl+G drive since item 28.

    After any Ctrl+G, in either mode, whether the drive took it or not, the firmware sends no IDENTIFY until the ATAboy is power-cycled (until item 28: until Auto Detect). Debug I and Debug S (the seek test starts with IDENTIFY) say "Refused: Ctrl+G drive, no IDENTIFY. Nothing sent." and send nothing, and the IDENTIFY routine itself refuses too, whoever calls it. So pass-through and READ LONG stay refused for as long as the Ctrl+G geometry is shown. Before, typing I on the Debug screen after a Ctrl+G sent the drive IDENTIFY.

    The power-up default mode is refused if this ATAboy has sent a 91h since it was switched on, by any route: an old-mode Ctrl+G, a CHS read after a reset, Auto Mount's geometry. The box says "Refused: 91h already sent. Power-cycle drive and ATAboy." and stays in the old mode. Whether a drive keeps a 91h's translation through the reset on the IDE reset line isn't known for the CP3044, and if it did, this mode would read other sectors with good status. This check can't see a 91h sent before the ATAboy was switched on, by another controller or by this one before only the ATAboy was power-cycled, so the drive itself must still be power-cycled, and allowed to spin down, before a mount in this mode. Whether RESET- undoes a 91h has to be measured on a donor before this mode is used on a drive that matters.

    The trade-off, and neither side of it has been tried on a CP3044. This mode is only right if the drive really comes out of reset at the geometry typed in. The firmware can't check that: with no IDENTIFY and no 91h, the drive never says anything to check against. If the geometry typed in is wrong, reads come back with good status from other sectors; the host tests show exactly that. Item 22's mode tells the drive the geometry instead, every time. By the CP3024's text, a 91h of 4/40 keeps native addressing with the same geometry, so for 522/4/40 it should come to the same thing. But that text is about a sibling, not this drive, and the same text says a 91h the drive can't use isn't reported. Which mode to use is the operator's decision; I'm not claiming either one is safer.

    One gap: F10 saves the geometry but not the mode. After a power cycle Mount won't use a saved geometry on its own (it wants a detection or a Ctrl+G first), but Auto Mount will, and Auto Mount resets the drive, sends it IDENTIFY and then the 91h. F10 refuses to save a Ctrl+G geometry while Auto Mount is on, but Auto Mount can be switched on after saving. Keep Auto Mount off and don't save a geometry for a drive like this.

28. **Review fixes that reach beyond Ctrl+G, and three that tighten it.** From an adversarial review of the bus, power and the USB host's own traffic. Built and host-tested, not yet run on hardware.

    **The end of every read is checked.** A READ SECTORS used to succeed as soon as the last block had been read, without ever reading the drive's final status. A drive that lost power just after offering its last block (the Rev .6 board then reads FFFFh and a status of FFh), or that ended the command with ERR or with a device fault (DF), handed the host a sector that was never good, with good status. Now, after the last block, the firmware reads Alternate Status once and waits for BSY and DRQ both to clear, giving DRQ up to 1 ms to fall (a drive may drop it a moment after the last word, as READ LONG found in 0.6f3p9); only then are DRDY, ERR and DF judged. Otherwise the last sector fails like any other failed sector: the sectors before it go to the host, it doesn't. A status of FFh or 7Fh vouches for nothing: the block read just before it only counts once a sane status has followed. A command that runs out of time with the status still floating is recorded as "no drive" in Debug E, and the drive is reset as after a timeout. READ LONG gets the same end check; DF now counts as an error there, and a drive still busy at the end is no longer taken as done.

    (Corrected later on 2026-09-25, after a second review of these fixes. The first version failed a read as "no drive" after 50 ms of FFh, but FFh is a legal status for a busy drive, and a working drive showing it through a slow sector was failed and reset; now a floating status is waited on like BSY, within the command's time. The first version also judged the status the moment BSY cleared, so a drive whose DRQ fell a few microseconds late failed the last sector of every command and was soft-reset twice each time; the 1 ms settle fixes that.)

    **A drive that resets on its own is noticed.** A drive that resets itself (a power glitch, a brown-out, an internal reset) drops its 91h, and nothing need show on the bus: it can be ready again before the next command. Every CHS address after that was worked out through the drive's own default translation, and read other sectors with good status. 91h still goes out once per mount (and after the firmware's own resets). After every CHS command that ends well, the firmware leaves A5h and 5Ah in Sector Count and Sector Number, which an idle drive keeps; any reset puts its diagnostic signature (01h, 01h) there instead. Before the next CHS command both are read back, which costs two register reads and no drive command. If they changed, the drive reset itself: it's recorded (Debug E shows "[Last Failed I/O] drive reset itself before LBA n", and two lines, "Self-resets N, last LBA n" and "Self-resets: 91h again N, failed N"; until 2026-09-26 the counts were one line, which a long LBA cut short), and in the 91h mode one 91h goes out before the command. In the power-up default mode no 91h is ever sent: that command fails instead, so the host and the log both see it, and the next one goes ahead. The sentinel is read back when it's written, with BSY clear, and on the first 8 commands of each mount again 1 ms later. A drive that doesn't keep it (a pre-ATA controller might use those registers itself, or write its own values a moment after clearing BSY) gets no check for the rest of that mount: Debug E says "Self-reset check OFF: drive does not keep SC/SN", nothing fails and no 91h is sent because of it, and the host decides what that means. A new Ctrl+G tries again. What this can't see: a reset in the microseconds between the check and the command, one after a command that failed (nothing is left armed then), and, in the 91h mode, a reset that leaves those registers alone, which a drive older than ATA isn't bound to change (the second review's C3-2; the power-up default mode doesn't care, as a reset restores the geometry in use). The procedure's verify pass is still the check for those. Whether a drive keeps host-written values in those two registers while idle has to be measured on a donor; ATA and the WD1003 task file both say it does.

    (Corrected again later on 2026-09-25, after a third review. The counts were first also put in READ BUFFER bytes 24 to 31, but imagelba refuses a salvage buffer whose bytes 24 to 31 aren't zero, so after the first self-reset every salvage run would have stopped. READ BUFFER is back to its 0.6f3p9 layout, byte for byte; the counts are in Debug E only. The sentinel was also not read back when written, so a drive that doesn't keep it would have failed every other command in the power-up default mode, or had 91h sent every other command in the 91h mode.)

    (Corrected later on 2026-09-25. The first version of this fix sent 91h before every CHS command: about 10,440 for one pass of a CP3044 at 522/4/40, and period Conner manuals say the drive saves each 91h to its EEPROM. That meant wear, and a write window on every command, on a specimen. It also took the status 1 us after each 91h as its answer, so a drive slow to raise BSY had its next command written while still busy, and an error left by a failed read was taken as 91h refused and recorded as "no geometry". 91h now waits for the drive to have visibly started it, as Ctrl+G's own 91h does.)

    **Auto Detect asks first, and is refused after a Ctrl+G.** Auto Detect sends the drive IDENTIFY, and Enter on the main menu's first item ran it at once. It now asks "Auto Detect sends IDENTIFY. Run it (Y/N)?", and only Y runs it. After any Ctrl+G it says "Ctrl+G drive: Auto Detect refused. Press a key" and sends nothing, until the ATAboy is power-cycled. That rule is kept in RAM only: saving it in the settings flash would change their layout, and a flag that only a menu action clears would need its own safeguards. So the procedure for a drive that must never get IDENTIFY is: power the ATAboy first and let it reach the main menu, with Auto Mount off, and only then power the drive; after an ATAboy reboot with the drive powered, nobody presses Enter on Auto Detect. Auto Mount at power-up still sends IDENTIFY, as item 22 says.

    **A Ctrl+G drive is write protected** whatever Features says, until the ATAboy is power-cycled: WRITE(10) is refused and both MODE SENSE answers say write protected.

    **IORDY.** It is never believed for a Ctrl+G drive (the CP3044's manual marks that pin reserved). And the PIO programs, which wait for IORDY with no limit, now get 1 ms per word from the C side: a cycle held longer is released by taking IORDY as high, and the block it was part of fails and the drive is reset.

    **At power-up the firmware no longer pulses the drive's reset line.** Making the pins outputs drove RESET-, CS0-, CS1- and the transceiver enables low until the IDE code set them, for an unmeasured time: an extra reset of the drive at every ATAboy boot. They are set high first now. Not host-testable beyond the order of the two steps.

    **After the Ctrl+G reset, a floating bus (FFh) is waited for** up to the same 45 seconds as a busy one, since a drive older than ATA may not drive the bus at once; only FFh all that time is "no drive answered".

29. **Holistic review of the whole firmware, before it goes on hardware (2026-09-26).** Built and host-tested, not yet run on hardware.

    **Reads: between blocks, as ATA says, and a phantom never gets out.** After each block of a multi-sector READ SECTORS the firmware went straight back to polling status, and took the first status with DRQ set as the next block. A drive whose DRQ stayed up a moment after a block had that same status read as the next block's DRQ: 256 words read while nothing drove the bus (FFFFh on this board), every later block one out, and all of it handed to the host with good status. ATA-6 (9.5) says a drive drops DRQ and raises BSY after each block, for no set time, and a polling host waits one PIO cycle (600 ns) and then takes BSY clear with DRQ set as the next block. So now, after each block but the last: the first Alternate Status read counts (it comes a few microseconds after the last word, past that cycle), and BSY set or DRQ clear in it or any read after is the drop; a fresh INTRQ counts too (the line read low right after the status that gave the block, high now; a line stuck high or not wired never counts); with neither within 1 ms, DRQ is taken as the next block, as ATA's host does, and Debug E counts it ("Blocks taken with no drop seen before: N"). If that DRQ was stale, the blocks are one out and the drive still has data on offer after the last one: that is checked at the end of every command, and it fails the whole command with nothing handed over (it used to hand over all but the last). In the simulator, drives busy between blocks for 0 to 10 microseconds, with register reads from instant to 4 microseconds, read with no failure and no reset, and a DRQ left up from 200 ns to 5 ms gives either the real data or a whole command failed, never a wrong sector. Writes (donor drives only; a Ctrl+G drive is write protected) get the same rule between blocks, and a write that ends with DF, or with DRQ still up 1 ms after the last word, is not taken as done. A device fault (DF) during a read now ends it like ERR, and the drive is reset.

    (Corrected on 2026-09-26 after a second holistic review. The first version of this fix threw the first status read away and failed the whole command, with a soft reset, whenever it saw no drop within 1 ms. A drive whose gap between blocks is shorter than the firmware's first counted look, which ATA allows, then failed every multi-sector read and was soft-reset once a command: about 10,000 resets in one pass of a CP3044 read 8 sectors at a time. 83b8cfb had read those drives correctly.)

    **No more than 16 heads, anywhere.** 17 heads went to the drive as 1 in 91h (`(17 - 1) & 0Fh`) while the firmware addressed head 16 as head 0: other sectors, good status. The Auto Detect picker's manual row and F: Force now refuse what Ctrl+G refuses (heads 1 to 16, cylinders 1 to 65535, sectors 1 to 255), a picker row whose heads exceed 16 (IDENTIFY word 3 above 16, or the LARGE translation's 32 and more, which could never have worked) isn't applied, 91h and every CHS address refuse more than 16 heads whatever set them, and saved settings with more are not loaded. Nothing is cut to four bits any more.

    **Bus timing.** Every task file access is an 8-bit transfer, whose ATA mode 0 minimum strobe is 290 ns, not the 165 ns of 16-bit data. The write strobe was 300 ns. Now DIOW- is 400 ns with 200 ns data setup, DIOR- 500 ns with the data sampled at 400 ns, every figure at least 100 ns over its minimum; `ataboy.pio`'s header has the table, and a host test works the figures out from the file and fails below that. The state machines' clock divider is worked out from the system clock that is actually running, rounded up so a cycle is never shorter than 100 ns (it was a fixed 15, right only at 150 MHz). Each word costs 100 to 200 ns more; that doesn't show behind USB.

    **The settings sector** has a CRC-32 and every field is range-checked when it's loaded; anything wrong (a torn write, a flipped bit, an older layout) loads the defaults: write protect on, Auto Mount off. Settings saved by any earlier build load as defaults once. **F10 and Load Setup Defaults** now wait for a USB command still running, as the other bus users do, or say so and save nothing.

    **IDENTIFY** is only taken once the command has ended cleanly (BSY and DRQ clear, no ERR or DF), and its 48-bit capacity words are only used when word 83 says the drive has the 48-bit feature set.

    **Faults.** A HardFault on either core used to lock the core up with the bus as it was, possibly with CS0- asserted and DIOR- held low. Now it runs on a stack of its own, releases the bus (data lines as inputs behind both transceivers disabled, DIOR-, DIOW-, CS0- and CS1- negated, RESET- not asserted, the state machines stopped), holds the other core in reset and stops. The handler and everything it calls run from RAM, so it works even during a settings save, when the flash can't be read. It doesn't reboot: a reboot would re-enumerate USB mid-session, clear the no-IDENTIFY rule and could run Auto Mount. Unplug to recover. It also records the core, PC, LR and CFSR in RAM that a warm reset keeps, and Debug E shows them ("Fault before this boot: ..."), but on this board you will almost never see that line: the ATAboy is powered from USB, so unplugging it, the only way out, is a power cycle and loses the record. It survives only a reset with power kept, which this board has no button or debug port for. **Stacks:** core 0 has all 4 KB of its scratch bank and core 1 its own 8 KB (it measured 2 KB deep against a 2 KB stack), both with the RP2350's stack limit set at the bottom, and core 1 checks a canary above its limit on every pass of its loop.

    **Pins.** The firmware was built as a Raspberry Pi Pico 2, whose board file names GPIO 25 (CS1- here) as its LED and GPIO 23 and 24 (RESET- and CS0-) as power pins. It is now built for its own board file, `boards/ataboy_rev6.h`, which names none of those, and the build refuses a board file that does. After a warm reset (Ctrl+F flashing), RESET-, CS0-, CS1- and the transceiver enables used to fall to their pad pull-downs for a moment while the firmware took them over; they are now driven high before they are switched. The main screen shows the chip's stepping (right panel, "Chip: RP2350 A4").

The fork's build calls itself `0.6f3p10-palimpsest` and shows `v0.6f3p10 (fork)` in the setup screen (0.6f3p1 before items 6 to 15, 0.6f3p6 before 16 to 21, 0.6f3p7 before 22, 0.6f3p8 before 23 to 26, 0.6f3p9 before 27 to 29), so it can't be mistaken for a stock v0.6f3.

## Builds

Every push to `main` or a `palimpsest/**` branch, every pull request and every `v*` tag runs [`build-firmware.yml`](.github/workflows/build-firmware.yml). It builds the fork firmware and upstream's v.6f3 with the exact versions the sources ask for (Arm GNU Toolchain 14.2.Rel1, Pico SDK 2.2.0, picotool 2.2.0-a4), and uploads the `.uf2`, `.elf`, `.bin`, `SHA256SUMS` and `picotool info` output.

The builds are reproducible. The build date is pinned to the commit date, and the same commit gives the same bytes on Windows and on the Linux runners. There's also a job that rebuilds upstream's published `ATAboy6f3.uf2` from source and compares it byte for byte. It matches.

Tagging `vX.Y.Z` publishes a pre-release with the files attached.

To build locally with the same toolchain:

```
cmake -S "FW source/v.6f3p1" -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DPICO_SDK_PATH=<sdk> -DPICO_TOOLCHAIN_PATH=<toolchain> \
  -Dpicotool_DIR=<picotool>
ninja -C build
```

The board is set in `CMakeLists.txt` (`ataboy_rev6`, item 29); a `-DPICO_BOARD` on the command line is overridden.
